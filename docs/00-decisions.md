## Ordering, SLA and discounts

| # | Topic | Decision | Source |
|---|---|---|---|
| D8 | Walk-in "Order ID" (PRD §13) | Staff opening a table creates a **table session** with a short public code (e.g. `UB-4821`) and a 4-digit **PIN**. Customer enters code + PIN on the storefront to join. Code alone reveals nothing. | Default |
| D9 | Session scope | The code identifies the whole table visit. All later orders join the same session and the same final bill. Several people at the table may join with the same code + PIN and share one cart. | Default |
| D10 | Finish | Customer's **Finish** locks the session and produces the final bill. Staff can reopen, and staff can close a session the customer abandoned. | Default |
| D11 | Timer granularity | Each order (kitchen ticket) has its own SLA timer; its discount applies only to that order's lines. Order-level SLA: served when all items are served (PRD §14). | Default |
| D12 | Discount base | Food subtotal of the order **before tax and service charge**. Tax is then computed on the discounted amount. | Default |
| D13 | Discount cap | Default maximum 20%; configurable per restaurant. | Default |
| D14 | Discount formula | For `elapsed > serving_minutes`: `pct = min(max_pct, initial_pct + (ceil((elapsed − serving_minutes) / interval) − 1) × increment)`. With defaults (15, 2, 5, 2) this is exactly the PRD table. Edits/cancellations do not reset the timer. | Default |
| D15 | Policy snapshot | The full discount policy is copied (JSON) onto the order's SLA row when the timer starts. Policy edits never change running or past orders. | PRD |

| D53 | Live updates | Socket.IO connections send the access token; joining a branch room is re-checked against the database (membership + branch access). Events are emitted after commit; clients refetch the board. | Phase 5 |

| D55 | Booking policy | One policy per branch: online queue on/off, online reservations on/off, free and/or paid bookings, fee, slot length (15/30/60), table hold (dining) time, grace period, minimum notice, days ahead, party size range, free-cancellation window, refund on no-show. Defaults apply until the owner saves. Each booking keeps a snapshot of the policy it was made under. | Phase 6 |
| D56 | No double booking | Each booking holds one table for [start, start + dining time). PostgreSQL refuses overlapping holds on the same table (GiST exclusion constraint), so two guests can never get the same table, even at the same instant (tested concurrently). The smallest table that fits is chosen. | Phase 6 |
| D57 | Payments | Pluggable gateway: `mock` (development, default) and `razorpay` (set `PAYMENT_PROVIDER=razorpay` + keys). A paid booking is held for 15 minutes as "awaiting payment" and is confirmed **only** by a signature-verified webhook; repeated webhooks change nothing. A payment arriving after expiry/cancellation is refunded automatically. The mock checkout page (`/pay/mock/…`) exists only outside production. | Phase 6 |
| D58 | Cancellation & refunds | Guest cancels at least *free-cancel hours* before → fee refunded in full; later → no refund. Restaurant cancels → always a full refund. No-show/expiry → refund only if the policy says so. | Phase 6 |
| D59 | Expiry job | Every minute the worker: expires unpaid bookings past the payment hold, expires confirmed bookings past start + grace (no arrival), and marks a booking's table "reserved" 30 minutes before. Checked-in bookings are never touched. Rows are locked with SKIP LOCKED, so several workers are safe. | Phase 6 |
| D60 | Arrival | Staff confirm arrival at the door ("Confirm arrival") → guests are seated (table session code + PIN) and the server time is recorded (SLA start for paid pre-orders, Phase 8). When the guests leave, the booking completes. | Phase 6 |
| D61 | Queue | Tokens `A-001…` per branch per day; one active token per guest per branch; guests join online (signed in with mobile) or staff add walk-ins. Estimated wait = how many parties are ahead vs. free/suitable tables × average table time of the last 14 days (default 45 min). Staff can notify ("table ready", optionally holding a table), seat, reorder, skip, mark no-show. Guests follow their place live; a printable QR code at the door opens the queue page. | Phase 6 |
| D62 | Notifications | In-app (Socket.IO room per user) plus a server log line for now; SMS/WhatsApp providers plug into the same `notify_guest` call later (D28). | Phase 6 |
| D63 | Dish options | Sizes (variants) replace the base price and one must be chosen; extras come in groups with min/max choices; optional serving-time windows per weekday; per-branch "not served here" and price override; tax % per dish (default 5) and free-text tags. The owner edits all options of a dish in one "Sizes, extras & times" dialog (saved as a whole). | Phase 7 |
| D64 | Server-side pricing | Every order is priced by the server from the live menu (branch price/size + extras, tax per dish, rounded per line). Lines keep snapshots (name, size, extras, prices), so later menu edits never change an order. Dishes are archived, never deleted. | Phase 7 |
| D65 | No duplicate orders | Checkout sends an `Idempotency-Key`; the same key returns the original order (HTTP 200) instead of creating a second one. Keys are namespaced per sender (table, customer or staff member). Order numbers are per branch per day (`001`…), unique even under concurrent orders. | Phase 7 |
| D66 | Order ID + PIN for guests | Guests at a table do **not** need an account: they enter the order ID and PIN from the waiter ("Have an order ID?") and get a table token (12 h). A new PIN logs out old links; closing the table stops new orders. Wrong-PIN attempts are limited (5 per code / 15 min, 30 per device IP). | Phase 7 |
| D67 | Order statuses | Placed → Accepted → Preparing → Ready → Served. The kitchen (`kitchen.operate`) moves orders up to Ready; only `orders.mark_served` (waiter/manager/owner) marks Served — Ready ≠ Served. Guests can cancel only before the kitchen accepts; staff can cancel until Ready, with a reason. | Phase 7 |
| D68 | Pre-orders | Only paid bookings (confirmed = paid) can pre-order; free bookings get `PREORDER_NOT_ALLOWED`. Pre-ordered dishes are checked against serving times at the booking time. The kitchen cannot start a pre-order before Confirm Arrival (`PREORDER_NOT_ARRIVED`); arrival attaches the pre-orders to the guests' table. | Phase 7 |
| D69 | Cart | The cart lives in the browser, one per restaurant (switching restaurants never mixes dishes); prices shown there are a preview. The order goes to the guest's table (after order ID + PIN) or, for a paid booking, as a pre-order. | Phase 7 |
| D70 | Order types | `walk_in` (guest at a walk-in/queue table), `booking` (guest at a table seated from a reservation), `staff` (placed by a waiter), `paid_preorder` (before arrival). Phase 8 uses these for the 15-minute promise. | Phase 7 |
| D71 | Timer start per order type | `walk_in`, `staff` and `booking` (free booking — guests are already seated): when the kitchen first accepts (or starts preparing). `paid_preorder`: at Confirm Arrival (`staff_confirmed_at`), never at order time; accepting later does not restart it. Server UTC only, stored once — a database trigger blocks rewriting the start, deadline or policy copy. | Phase 8 |
| D72 | Served / cancelled | Served (all items delivered, order-level SLA) freezes the discount at the serving time. Cancelling stops the timer and removes any discount. | Phase 8 |
| D73 | Policy screen | Owner-only (`discounts.policy.manage`), one policy per restaurant; WaitLess defaults (15 min, 2 %, +2 % per 5 min, cap 20 %, all order types, food-subtotal base) apply until saved. Options: on/off, serving minutes, first %, interval, increment, cap, eligible order types, base (food before tax, or order total incl. tax). Saving affects new timers only (D15); changes are audited. | Phase 8 |
| D74 | Live timer | Browsers count down locally from `started_at`/`deadline_at`, corrected by the response's `server_time`; they show the discount with the same formula as the server. The worker (`sla_tick`, every 15 s) wakes each timer just after its boundary (15, 20, 25 … min), stores the `sla_delay` discount and pushes `orders.changed` (the existing event is reused instead of separate `sla.started` / `discount.changed`). | Phase 8 |
| D75 | Where the discount shows | Guest table page: promise banner, per-order timer, "x % off (₹y)", totals with the discount and tax on the discounted food. Kitchen tickets turn red only after the order's own deadline. Orders page and My orders show the discount. The final bill (Phase 10) reads `order_discounts`. | Phase 8 |
| D76 | Stock engine | The movement ledger is insert-only (trigger) and is the truth; `inventory_stock.on_hand` changes in the same transaction under a row lock. Valuation uses the weighted average cost of what came in (opening, purchases, additions, transfers); the item's purchase price follows the last purchase. | Phase 9 |
| D77 | Never below zero by hand | Wastage, damage, returns and transfers cannot take stock below zero (409 `INSUFFICIENT_STOCK`). Order consumption may go negative so the kitchen is never blocked; the item then shows "out" until a count correction or delivery. | Phase 9 |
| D78 | Manual changes | Types: opening (once per item and branch), add stock, wastage, damage, return to supplier, count correction (enter what was counted; the difference is recorded). All need a reason (opening defaults to "Opening stock"), store the user and are audited. The unit of an item is locked once it has stock history. | Phase 9 |
| D79 | Recipes | Quantities per portion in a compatible unit (g/kg, ml/l; pcs/pkt/box as is). Lines for a size replace the base recipe for that size. Add-ons have no recipe yet. Deducted on Accept (D22) by matching the order line's size name; reversal on staff cancel after Accept. | Phase 9 |
| D80 | Purchases & transfers | PO-0001 numbering per restaurant; draft → ordered → received (short deliveries re-bill what arrived; expiry dates required for items that track expiry) · cancel before receipt. Supplier payments up to the total. Transfers (TR-0001): stock leaves on send and arrives only when the receiving branch presses Receive; cancel returns it to the sender. | Phase 9 |
| D81 | Alerts | Low = at or below the reorder level, out = zero or less. When a movement crosses the reorder level, staff with `purchases.manage` for that branch get an in-app notification. Suggested order = up to twice the reorder level (at least the minimum stock). Expiring = batches received with an expiry date within 7 days while stock remains. | Phase 9 |
| D82 | Bills follow the visit | A table visit has one bill by default; every order line is on exactly one bill (unique key), so nothing is charged twice. Open bills are recalculated from the orders (cancelled orders drop off). The first payment locks a bill; orders after that go to a new bill ("Bill 2"). | Phase 10 |
| D83 | Bill arithmetic | Food → serving-time discount per order (split over its lines in proportion, so split bills still add up) → manual discount (% or amount, on food after the serving-time discount) → taxable food → service charge (% of taxable food, taxed at its own rate, default 5 %) → GST per rate on the bill (shown as CGST + SGST halves, or one line) → booking fee credit → round off to the rupee (optional). Every step rounds half-up to the paisa. | Phase 10 |
| D84 | Limits | Manual discounts need `billing.discount.apply` and a reason; non-owners stay within the owner's manager limit (default 10 %). Refunds need `payments.refund`; non-owners up to the refund limit (default ₹2,000). Writing off an unpaid bill (void) needs `billing.discount.apply` and a reason. All are audited. | Phase 10 |
| D85 | Payments | Cash (with cash handed over → change), UPI, card, "other" (named, e.g. a meal card) taken by staff; online (gateway) paid by the guest. A payment cannot exceed what is due; the same `Idempotency-Key` never charges twice. Splitting equally = several payments of equal shares. An online payment that arrives after the bill was paid at the counter is refunded automatically. | Phase 10 |
| D86 | Invoices | Paid in full → an immutable invoice INV-000001 (prefix configurable) holding a snapshot of everything printed; a database trigger forbids edits. A refund issues a credit note CN-000001 against it. ₹0 bills (covered by credit/discounts) close with a ₹0 invoice. PDF: A4 or 80 mm receipt; amounts print as "Rs" (built-in fonts have no ₹). | Phase 10 |
| D87 | Finish & close | The guest's **Finish** stops new orders and shows the final bill with "Pay online". Staff can reopen a finished table. "Guests left" (close) requires every bill paid (or written off); ₹0 bills are settled automatically. | Phase 10 |
| D88 | Billing settings | Service charge %, its GST %, CGST/SGST or single GST line, round off, invoice prefix, legal name, GSTIN, address, footer, enabled payment methods and the name of "Other". Owner (`settings.manage`); open bills use new settings on their next recalculation, paid bills keep theirs. | Phase 10 |
| D89 | Dashboard figures | Today = the branch's local day. Revenue = paid bills minus refunds; discounts = serving-time + manual on paid bills; average wait = queue join → seated; average serving time = order timer start → served; delayed = served after the deadline plus timers running late now; low stock = items low or out at the branch. Money figures only for staff who can see sales or billing. | Phase 11 |
| D90 | Reports | Sales, payments by method, orders, serving time & delays, discounts, reservations, queue (Professional: `analytics.basic`); best-selling dishes and busy hours (`analytics.advanced`, Enterprise). Up to one year, per branch or all allowed branches. The chart, the table and the CSV come from the same response. Charts: Chart.js, loaded only on chart pages. | Phase 11 |
| D91 | Plans are data | Features (on/off) and limits live in `plan_features`; the Super Admin creates and edits plans in the UI. Limits and features are read on every request, so changes and plan assignments apply immediately (acceptance test 15). Plan codes cannot change. | Phase 11 |
| D92 | Subscription lifecycle | Hourly job: trial or period ends → free plans roll on; paid plans get a renewal invoice and become "payment due" with a grace period (default 7 days) → then expired (paid features stop). Paying the renewal invoice → active for that period. Auto-renew off → cancelled at period end. Super Admin can assign/upgrade/downgrade (immediate), extend, renew now, stop/resume renewal, cancel. | Phase 11 |
| D93 | WaitLess invoices | WL-000001, amount + GST (default 18 %), due in 7 days; paid online by the owner (same verified webhook) or recorded by the Super Admin (bank, UPI, card, cash, waived); voidable while unpaid. Completely separate from restaurant bills (D18). | Phase 11 |
| D94 | Website content | Sections (home, how it works, features, for restaurants, about, contact, branding/announcement, terms, privacy) are JSON with fixed fields; defaults are the built-in copy; edits show within a minute (cache). Maintenance banner and sign-up switch are platform settings. | Phase 11 |
| D95 | Support & audit | Tickets from the website form and from restaurants (Settings → Help) with status, priority, owner (a WaitLess admin) and internal notes that restaurants never see. The audit log viewer filters by action, dates, restaurant and "administrators only". | Phase 11 |
| D96 | Notification wording | Per event: title/text with `{title}` / `{body}` placeholders, or switched off; applied to every in-app notification (cached 60 s). SMS/WhatsApp/e-mail channels use the same templates when providers are connected (Phase 12). | Phase 11 |
